Verify each item against current official docs before building the part that depends on it. Record the answer, the date, and the source URL under each item. These APIs changed several times in 2026, so do not trust memory or older blog posts.

## M0: before writing code

1. **Name availability.** Is the name free on npm and as a GitHub org or repo? If not, choose another name.
   - **Answer (2026-10-11):** `agentsync` is taken: npm `agentsync@1.0.0` (an unrelated agent-config tool, published 2026-09-02; `npm view agentsync`) and the GitHub org `https://github.com/agentsync` exists, with a dozen unrelated repos of that name. Renamed to **`agentroom`**: free on npm (`npm view agentroom` returns nothing) and no GitHub user or org of that name (`gh api users/agentroom` is 404). A few unrelated repos use the name (largest `liuyixin-louis/agentroom`, 49 stars), which does not block an npm package or a new org. Share-code prefix is now `ar1_`, state dir `~/.agentroom`, HKDF info strings `agentroom/v1/*`. Creating the GitHub org/repo is a human step.
2. **MCP TypeScript SDK.** Current package name, version, stdio server API, and how to declare tools and prompts.
   - **Answer (2026-10-11):** The SDK is on its **v2** line, split into packages: `@modelcontextprotocol/server@2.3.1` (depends on `@modelcontextprotocol/core` and `zod@^4.2.0`), `@modelcontextprotocol/client@2.3.1`, engines `node >= 20`. The old `@modelcontextprotocol/sdk` (latest 1.32.1) is the v1 line, maintenance only. Use v2. Sources: README at https://github.com/modelcontextprotocol/typescript-sdk ("`main` is v2, the stable release line, implementing the 2026-07-28 spec"), docs at https://ts.sdk.modelcontextprotocol.io/v2/ and `docs/servers/{tools,prompts,errors}.md`, `docs/advanced/schema-libraries.md`, `docs/testing.md` in that repo.
   - API: `import { McpServer } from '@modelcontextprotocol/server'`; `import { StdioServerTransport, serveStdio } from '@modelcontextprotocol/server/stdio'`; `import * as z from 'zod/v4'`. `new McpServer({ name, version })`; `server.registerTool(name, { title?, description, inputSchema: z.object({...}), outputSchema?, annotations? }, async (args) => ({ content: [{ type: 'text', text }], structuredContent?, isError? }))`. Raw-shape `inputSchema: { a: z.string() }` is deprecated; pass a schema object. Any Standard Schema that emits JSON Schema works (Zod v4, ArkType). Schema-rejected arguments come back as an `isError: true` result; thrown errors become `isError: true` with the message as text. `server.registerPrompt(name, { title?, description, argsSchema: z.object({...}) }, (args) => ({ messages: [{ role: 'user', content: { type: 'text', text } }] }))`. Transport: `await server.connect(new StdioServerTransport())` or `serveStdio(createServer)`. stdout is the protocol channel; log with `console.error`. Tests: drive the server in-process through `Client` from `@modelcontextprotocol/client` (`docs/testing.md`), or spawn the stdio binary with `StdioClientTransport`. Inspector: `npx @modelcontextprotocol/inspector <command>`.
3. **Claude Code MCP config.** Current way to add a stdio MCP server per project and per user (`claude mcp add` flags, `.mcp.json` format).
   - **Answer (2026-10-11, https://code.claude.com/docs/en/mcp and `claude mcp add --help`):** `claude mcp add [--scope local|user|project] [--env K=V...] --transport stdio <name> -- <command> [args...]`. Default scope is `local` (stored in `~/.claude.json` under `projects.<path>.mcpServers`); `user` is also `~/.claude.json`; `project` writes `.mcp.json` in the repo root. Put `--transport stdio` between `--env` and the name or the name is parsed as an env pair. `claude mcp add-json <name> '{"type":"stdio","command":"...","args":[...],"env":{...}}'` takes a full entry. `.mcp.json` shape: `{ "mcpServers": { "<name>": { "type": "stdio", "command": "...", "args": [...], "env": {...}, "timeout"?: ms, "alwaysLoad"?: bool } } }`. An entry without `type` is read as stdio. `${VAR}` and `${VAR:-default}` expand in `command`, `args`, `env`, `url`, `headers`. Project-scoped servers need interactive approval once (`claude mcp reset-project-choices` resets). Timeouts: `MCP_TIMEOUT` (startup, ms), `MCP_TOOL_TIMEOUT` (per call; default about 28 h, so the `wait` tool's 50 s cap is not needed for Claude Code), per-server `timeout` field, `MAX_MCP_OUTPUT_TOKENS` (default 25,000). Tool search is on by default, so tool definitions are deferred until needed; server `instructions` matter and are truncated at 2,048 chars. MCP prompts appear as `/servername:promptname` and `/mcp__servername__promptname`, arguments split on whitespace. A tool can set `_meta["anthropic/requiresUserInteraction"]: true` to force a permission prompt on every call (prompt must reach a person; denied in `--permission-prompt-tool` mode). Decision: `agentroom install claude` runs `claude mcp add --scope user --transport stdio agentroom -- npx -y agentroom mcp --room <id>`; if `claude` is not on PATH, it writes a project `.mcp.json` instead (`~/.claude.json` is not a documented hand-edit target) and says so.
   - **Addendum (2026-10-11, M1 plan KTD15):** `agentroom` is not on npm until M4, so `npx -y agentroom mcp --room <id>` is used only when the running CLI resolves inside a `node_modules` directory (an installed copy). From a checkout, `install` registers the absolute `process.execPath` plus the absolute path of the running `dist/bin.js`. It first runs `claude mcp remove --scope user agentroom` (failure ignored), then `claude mcp add --scope user --transport stdio agentroom -- <command> <args...>`, both spawned with argument arrays, never a shell string. Without `claude` on PATH it merges `mcpServers.agentroom = {type:"stdio", command, args}` into `<cwd>/.mcp.json`, keeps other entries, aborts on invalid JSON without touching the file, and prints that the file should not be committed because it names the room id. `up`/`join --agent claude` run this after writing the room; other agents get the command printed.

## M3: Claude Code plugin

4. **Plugin manifest.** Current plugin format: can one plugin bundle an MCP server, slash commands, hooks, and a status line?
   - **Answer (2026-10-12, https://code.claude.com/docs/en/plugins-reference):** Yes for MCP server, commands/skills and hooks; **no for the main status line.** Layout: `.claude-plugin/plugin.json` (only `name` required; kebab-case; `version`, `description`, `author`, `license`), `.mcp.json` at the plugin root or inline `mcpServers` (`{"agentroom": {"command": "node", "args": ["${CLAUDE_PLUGIN_ROOT}/..."]}}`; `${CLAUDE_PLUGIN_ROOT}` resolves in `command`/`args`/`env`; `${CLAUDE_PLUGIN_DATA}` is a persistent per-plugin dir), `hooks/hooks.json` (`{"hooks": {"<Event>": [{"matcher": "...", "hooks": [{"type": "command", "command": "...", "args": [...], "timeout": 30}]}]}}`; quote `"${CLAUDE_PLUGIN_ROOT}"` in shell-form commands or use exec form with `args`), `commands/*.md` (older format, still works; namespaced `/agentroom:say`) or `skills/<name>/SKILL.md` (preferred; same frontmatter: `description`, `argument-hint`, `allowed-tools`, `model`, `disable-model-invocation: true` for user-only commands; `$ARGUMENTS`, `$0`, `$1` substitution). A plugin `settings.json` only applies `agent` and `subagentStatusLine`; every other key is dropped, so the plugin cannot set `statusLine`. `claude plugin validate ./plugin` checks the manifest. Local install for testing: `claude --plugin-dir ./plugins/claude-code`; distribution needs a marketplace entry (`marketplace.json`) or Anthropic's directory.
5. **Status line.** Can a plugin set it, or must settings be edited? How to chain with a user's existing status line?
   - **Answer (2026-10-12, https://code.claude.com/docs/en/statusline):** Settings only. `~/.claude/settings.json` (or project settings) gets `"statusLine": {"type": "command", "command": "<path or inline shell>", "padding": 0, "refreshInterval": <seconds, optional>}`. The script receives JSON on stdin (`session_id`, `cwd`, `workspace.current_dir`, `workspace.project_dir`, `model.display_name`, `context_window.used_percentage`, cost fields) and prints the line to stdout; ANSI colors and OSC 8 links are allowed; multi-line output is supported. Updates are event-driven with a 300 ms debounce and go quiet when the session is idle, so set `refreshInterval` (minimum 1) to keep the unread count current. Chaining: `agentroom install claude` saves the user's existing `statusLine.command`, writes `agentroom statusline --chain "<original command>"`, and the script runs the original with the same stdin and appends ` | agentroom ...`; if the original is absent it prints only its own segment. Uninstall restores the saved command.
6. **`UserPromptSubmit` hook.** Can it (a) read the raw prompt, (b) block the prompt from reaching the model, and (c) inject additional context? Exact output format.
   - **Answer (2026-10-12, https://code.claude.com/docs/en/hooks):** (a) Yes: stdin JSON `{"session_id", "transcript_path", "cwd", "permission_mode", "hook_event_name": "UserPromptSubmit", "prompt": "<submitted text>"}` (pasted placeholders arrive expanded). (b) Yes: print `{"decision": "block", "reason": "<shown to the user, not added to context>"}` and exit 0, or exit 2 with the message on stderr. The block message ends with `Original prompt: <text>` unless `hookSpecificOutput.suppressOriginalPrompt: true`; the typed text is still written to the transcript and prompt history, so a hook is not a way to keep text off disk (fine for `/say`, whose text is not secret). (c) Yes: `{"hookSpecificOutput": {"hookEventName": "UserPromptSubmit", "additionalContext": "<string>"}}`, or plain stdout on exit 0, is added alongside the prompt; it cannot replace the prompt. No matcher (fires on every prompt); default timeout 30 s, and a timed-out hook lets the prompt through without context unless `onFailure: "block"`. Declared in settings `hooks.UserPromptSubmit[].hooks[]` or a plugin `hooks/hooks.json` with the same shape.
7. **Slash commands and hooks.** When the user types a plugin slash command, does the `UserPromptSubmit` hook see the raw text before command expansion? If not, how should `/say` be implemented so the model never sees it?
   - **Answer (2026-10-12, https://code.claude.com/docs/en/hooks, https://code.claude.com/docs/en/slash-commands):** The docs do not state that `UserPromptSubmit` sees raw slash-command text. There is a dedicated **`UserPromptExpansion`** event: it fires "when a user-typed command expands into a prompt, before it reaches Claude" and can block the expansion. Stdin: `{"hook_event_name": "UserPromptExpansion", "expansion_type": "slash_command" | "mcp_prompt", "command_name": "<name>", "command_args": "<args string>", "command_source": "plugin" | ..., "prompt": "/<name> <args>"}`; matcher is on `command_name`; output `{"decision": "block", "reason": "<shown to user>"}` plus optional `hookSpecificOutput.additionalContext`. Decision: `/say`, `/approve` and `/send` are plugin commands (`disable-model-invocation: true`, with a body that only tells the model the hook already handled it, as a fallback) and the plugin's `UserPromptExpansion` hook, matched on those command names, posts the message and blocks the expansion with reason `Sent to <room> as <member> (human)`. A `UserPromptSubmit` hook handles `between` delivery (drains the queue into `additionalContext`) and, defensively, also catches a raw `/say ` prefix if it ever receives one. Commands are now skills; `commands/*.md` still loads.
8. **Channels.** Current status of Claude Code channels (research preview since v2.1.80 per the October 2026 research): capability name, how an MCP server pushes events, launch flag, Team/Enterprise admin requirement.
   - **Answer (2026-10-12, https://code.claude.com/docs/en/channels, https://code.claude.com/docs/en/channels-reference):** Still a research preview. Server declares `capabilities.experimental["claude/channel"] = {}` and pushes `mcp.notification({ method: "notifications/claude/channel", params: { content, meta: { key: value } } })`; the model sees `<channel source="<server>" key="value">content</channel>` (meta keys must be identifiers). Launch: `claude --channels plugin:<name>@<marketplace>` accepts only Anthropic's allowlist (telegram, discord, imessage, fakechat); anything else needs `claude --dangerously-load-development-channels plugin:<name>@<marketplace>|server:<name>`, interactive sessions only (ignored under `-p`). Team/Enterprise need `channelsEnabled: true` in managed settings (Owner); Console API-key users are allowed by default; Pro/Max are allowed. Caveat: on the v2 MCP client runtime Claude Code does not register a channel server that negotiates protocol revision 2026-07-28, and the docs' examples use the v1 `@modelcontextprotocol/sdk` `Server` class. Our server is on SDK v2 (2026-07-28). Decision: M3 ships `between` (hook) and `manual`; `live` via channels is deferred until channels leave preview or accept a 2026-07-28 server. The `send`-side etiquette for a future channel is already in `agentroom-rules`.
9. **Cross-session messaging.** Confirm it remains single-user (if Anthropic ships cross-account messaging, revisit scope).
   - **Answer (2026-10-12, https://code.claude.com/docs/en/channels "How channels compare"; observed in this build's own harness):** Claude Code offers agent-to-agent and session-to-session messaging within one user's own sessions (local, Remote Control, cloud) plus channels, Slack and cloud sessions. None of these crosses accounts or vendors. Scope unchanged.

## M4: other agents

10. **Codex CLI.** MCP config file location and format; tool-call timeout (sets the max `wait` duration); whether it has hooks equivalent to `UserPromptSubmit`.
   - **Answer (2026-10-12, https://learn.chatgpt.com/docs/extend/mcp?surface=cli, redirected from developers.openai.com/codex/mcp):** `~/.codex/config.toml` (or project `.codex/config.toml`, trusted projects only) with `[mcp_servers.<name>]` `command = "..."`, `args = [...]`, and `[mcp_servers.<name>.env]`. CLI: `codex mcp add <name> --env K=V -- <command> [args]`. Timeouts: `startup_timeout_sec` default 10, `tool_timeout_sec` default 60, so the `wait` tool's 50 s cap holds for Codex. Codex reads the MCP server `instructions` field as server-wide guidance, so the MCP server should set `instructions` to the `agentroom-rules` text. Hooks exist in Codex (a Hooks page is referenced; command hooks are not supported under cloud orchestration) but no prompt-submit equivalent was confirmed on the page fetched; the adapter relies on `AGENTS.md` for the inbox/wait instruction and the `watch` pane for human input.
11. **Gemini CLI / Antigravity CLI.** Which CLI is current for paid users; MCP config format; tool timeout; hooks.
   - **Answer (2026-10-12, https://geminicli.com/docs/tools/mcp-server/, https://geminicli.com/docs/hooks/):** The docs banner says Gemini CLI was replaced by Antigravity CLI for the unpaid tier and Google One users on 2026-06-18; paid users keep Gemini CLI, which is what the adapter targets. Config: `~/.gemini/settings.json` (user) or `.gemini/settings.json` (project, the default scope) with `mcpServers.<name>` = `{ "command", "args", "env" ($VAR references allowed), "cwd", "timeout" (ms, default 600000), "trust": false }`. CLI: `gemini mcp add [-s scope] [-t stdio] [-e K=V] [--timeout ms] [--trust] <name> <command> [args...]`. Hooks: configured in settings.json with `matcher` and `hooks: [{ "type": "command", "command", "timeout" }]`; events SessionStart, SessionEnd, BeforeAgent (after the user submits a prompt, before planning), AfterAgent, BeforeModel, AfterModel, BeforeToolSelection, BeforeTool, AfterTool, PreCompress, Notification; exit 0 with JSON (`{"decision": "deny"}` to block) or exit 2 with stderr as the reason. `GEMINI.md` is the project context file. The adapter writes the MCP entry and appends the inbox/wait snippet to `GEMINI.md`; a BeforeAgent hook for `/say` is possible later but out of v0 scope.
12. **Cursor.** MCP config location; whether background agents can use local stdio MCP servers.
   - **Answer (2026-10-12, https://cursor.com/docs/context/mcp, https://cursor.com/docs/agent/hooks):** `~/.cursor/mcp.json` (global) or `.cursor/mcp.json` (project) with `mcpServers.<name>` = `{ "type": "stdio", "command", "args", "env" }`; `${env:NAME}` interpolation in `command`, `args`, `env`, `url`, `headers`. Rules: `.cursor/rules` and `AGENTS.md` support were not on the pages fetched; the adapter appends to `AGENTS.md`, which Cursor and Codex both read per their general docs, and the builder should re-check before shipping.
