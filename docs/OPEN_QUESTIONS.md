## M0: before writing code

1. **Name availability.** Is the name free on npm and as a GitHub org or repo? If not, choose another name.
   - **Answer (2026-10-11):** `agentsync` is taken: npm `agentsync@1.0.0` (an unrelated agent-config tool, published 2026-09-02; `npm view agentsync`) and the GitHub org `https://github.com/agentsync` exists, with a dozen unrelated repos of that name. Renamed to **`agentroom`**: free on npm (`npm view agentroom` returns nothing) and no GitHub user or org of that name (`gh api users/agentroom` is 404). A few unrelated repos use the name (largest `liuyixin-louis/agentroom`, 49 stars), which does not block an npm package or a new org. Share-code prefix is now `ar1_`, state dir `~/.agentroom`, HKDF info strings `agentroom/v1/*`. Creating the GitHub org/repo is a human step.
2. **MCP TypeScript SDK.** Current package name, version, stdio server API, and how to declare tools and prompts.
   - **Answer (2026-10-11):** The SDK is on its **v2** line, split into packages: `@modelcontextprotocol/server@2.3.1` (depends on `@modelcontextprotocol/core` and `zod@^4.2.0`), `@modelcontextprotocol/client@2.3.1`, engines `node >= 20`. The old `@modelcontextprotocol/sdk` (latest 1.32.1) is the v1 line, maintenance only. Use v2. Sources: README at https://github.com/modelcontextprotocol/typescript-sdk ("`main` is v2, the stable release line, implementing the 2026-07-28 spec"), docs at https://ts.sdk.modelcontextprotocol.io/v2/ and `docs/servers/{tools,prompts,errors}.md`, `docs/advanced/schema-libraries.md`, `docs/testing.md` in that repo.
   - API: `import { McpServer } from '@modelcontextprotocol/server'`; `import { StdioServerTransport, serveStdio } from '@modelcontextprotocol/server/stdio'`; `import * as z from 'zod/v4'`. `new McpServer({ name, version })`; `server.registerTool(name, { title?, description, inputSchema: z.object({...}), outputSchema?, annotations? }, async (args) => ({ content: [{ type: 'text', text }], structuredContent?, isError? }))`. Raw-shape `inputSchema: { a: z.string() }` is deprecated; pass a schema object. Any Standard Schema that emits JSON Schema works (Zod v4, ArkType). Schema-rejected arguments come back as an `isError: true` result; thrown errors become `isError: true` with the message as text. `server.registerPrompt(name, { title?, description, argsSchema: z.object({...}) }, (args) => ({ messages: [{ role: 'user', content: { type: 'text', text } }] }))`. Transport: `await server.connect(new StdioServerTransport())` or `serveStdio(createServer)`. stdout is the protocol channel; log with `console.error`. Tests: drive the server in-process through `Client` from `@modelcontextprotocol/client` (`docs/testing.md`), or spawn the stdio binary with `StdioClientTransport`. Inspector: `npx @modelcontextprotocol/inspector <command>`.
3. **Claude Code MCP config.** Current way to add a stdio MCP server per project and per user (`claude mcp add` flags, `.mcp.json` format).
   - **Answer (2026-10-11, https://code.claude.com/docs/en/mcp and `claude mcp add --help`):** `claude mcp add [--scope local|user|project] [--env K=V...] --transport stdio <name> -- <command> [args...]`. Default scope is `local` (stored in `~/.claude.json` under `projects.<path>.mcpServers`); `user` is also `~/.claude.json`; `project` writes `.mcp.json` in the repo root. Put `--transport stdio` between `--env` and the name or the name is parsed as an env pair. `claude mcp add-json <name> '{"type":"stdio","command":"...","args":[...],"env":{...}}'` takes a full entry. `.mcp.json` shape: `{ "mcpServers": { "<name>": { "type": "stdio", "command": "...", "args": [...], "env": {...}, "timeout"?: ms, "alwaysLoad"?: bool } } }`. An entry without `type` is read as stdio. `${VAR}` and `${VAR:-default}` expand in `command`, `args`, `env`, `url`, `headers`. Project-scoped servers need interactive approval once (`claude mcp reset-project-choices` resets). Timeouts: `MCP_TIMEOUT` (startup, ms), `MCP_TOOL_TIMEOUT` (per call; default about 28 h, so the `wait` tool's 50 s cap is not needed for Claude Code), per-server `timeout` field, `MAX_MCP_OUTPUT_TOKENS` (default 25,000). Tool search is on by default, so tool definitions are deferred until needed; server `instructions` matter and are truncated at 2,048 chars. MCP prompts appear as `/servername:promptname` and `/mcp__servername__promptname`, arguments split on whitespace. A tool can set `_meta["anthropic/requiresUserInteraction"]: true` to force a permission prompt on every call (prompt must reach a person; denied in `--permission-prompt-tool` mode). Decision: `agentroom install claude` runs `claude mcp add --scope user --transport stdio agentroom -- npx -y agentroom mcp --room <id>`; if `claude` is not on PATH, it writes a project `.mcp.json` instead (`~/.claude.json` is not a documented hand-edit target) and says so.
   - **Addendum (2026-10-11, M1 plan KTD15):** `agentroom` is not on npm until M4, so `npx -y agentroom mcp --room <id>` is used only when the running CLI resolves inside a `node_modules` directory (an installed copy). From a checkout, `install` registers the absolute `process.execPath` plus the absolute path of the running `dist/bin.js`. It first runs `claude mcp remove --scope user agentroom` (failure ignored), then `claude mcp add --scope user --transport stdio agentroom -- <command> <args...>`, both spawned with argument arrays, never a shell string. Without `claude` on PATH it merges `mcpServers.agentroom = {type:"stdio", command, args}` into `<cwd>/.mcp.json`, keeps other entries, aborts on invalid JSON without touching the file, and prints that the file should not be committed because it names the room id. `up`/`join --agent claude` run this after writing the room; other agents get the command printed.

## M2: safety

17. **Agent environment markers.** Which environment variables mark a command as running in an AI agent's shell, so the CLI `say`, `approve` and `export` (and the M3 `watch` input) can refuse?
   - **Answer (2026-10-11, recorded in the M2 plan KTD18):** Refuse when any of these is set to a non-empty value, checked before the TTY test so the refusal names the cause: `CLAUDECODE` (Claude Code sets it in every subprocess, https://code.claude.com/docs/en/env-vars), `CLAUDE_CODE_CHILD_SESSION` (Bash, PowerShell and Monitor tools, hooks, status line; same page), `AI_AGENT` (Claude Code subprocesses since 2.1.120, https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md), `CODEX_THREAD_ID` (every Codex shell-tool command, not removable by `shell_environment_policy`, https://github.com/openai/codex/blob/main/codex-rs/core/src/exec_env.rs), `CODEX_CI` (Codex unified exec, https://github.com/openai/codex/blob/main/codex-rs/core/src/unified_exec/process_manager.rs), `CODEX_SANDBOX` (macOS Seatbelt only, https://github.com/openai/codex/blob/main/codex-rs/core/src/sandboxing/mod.rs), `GEMINI_CLI` (`run_shell_command` and `!` shell mode, https://github.com/google-gemini/gemini-cli/blob/main/docs/tools/shell.md), `CURSOR_AGENT` (Cursor staff forum post only, https://forum.cursor.com/t/cursor-cli-is-not-setting-cursor-agent-1-environment-variable-while-executing-bash-commands/132427). Not used: `CURSOR_TRACE_ID` and `CODEX_MANAGED_BY_NPM`, which mark the editor or the install rather than an agent shell. The list lives in `packages/cli/src/human.ts`; a vendor adding a marker needs a one-line change and a note here.
   - **Open:** Claude Code's IDE extensions also set `CLAUDECODE` in integrated terminals, so a person typing `agentroom say` there is refused. Alternative: refuse on `CLAUDE_CODE_CHILD_SESSION` always and on `CLAUDECODE` only without a TTY. Kept `CLAUDECODE` because `CLAUDE.md` invariant 2 and the M2 acceptance name it; until decided, run `say` from a standalone terminal.
18. **Secret scanner rules.** Which gitleaks rules port to JavaScript regexes, and how?
   - **Answer (2026-10-11, recorded in the M2 plan KTD4 and KTD24):** Provider rules come from gitleaks `config/gitleaks.toml` (https://github.com/gitleaks/gitleaks/blob/master/config/gitleaks.toml, master last changed 2025-11-20) with every inline `(?i)` rewritten as a whole-regex `i` flag, because Node 20 and 22 reject inline modifier groups. The AWS secret access key pattern is the keyword-anchored one from git-secrets (https://github.com/awslabs/git-secrets/blob/master/git-secrets); gitleaks has none. The gitleaks `EXAMPLE` allowlist for AWS ids is not ported. The private-key rule fires on the header line alone. The generic rule is a tightened version of gitleaks `generic-api-key`: case-insensitive keyword with suffix, optional `: Type`, a 20-150 character value that has a digit, is not only all-letter or short letter-plus-digit segments, and has Shannon entropy above 3.5 bits per character (`shannonEntropy` in https://github.com/gitleaks/gitleaks/blob/master/detect/utils.go); the 1 446-word stopword list is not ported. Fixtures are assembled from fragments at test time so the repository holds no credential-shaped string.

## M3: Claude Code plugin

4. **Plugin manifest.** Current plugin format: can one plugin bundle an MCP server, slash commands, hooks, and a status line?
   - **Answer (2026-10-12, https://code.claude.com/docs/en/plugins-reference):** Yes for MCP server, commands/skills and hooks; **no for the main status line.** Layout: `.claude-plugin/plugin.json` (only `name` required; kebab-case; `version`, `description`, `author`, `license`), `.mcp.json` at the plugin root or inline `mcpServers` (`{"agentroom": {"command": "node", "args": ["${CLAUDE_PLUGIN_ROOT}/..."]}}`; `${CLAUDE_PLUGIN_ROOT}` resolves in `command`/`args`/`env`; `${CLAUDE_PLUGIN_DATA}` is a persistent per-plugin dir), `hooks/hooks.json` (`{"hooks": {"<Event>": [{"matcher": "...", "hooks": [{"type": "command", "command": "...", "args": [...], "timeout": 30}]}]}}`; quote `"${CLAUDE_PLUGIN_ROOT}"` in shell-form commands or use exec form with `args`), `commands/*.md` (older format, still works; namespaced `/agentroom:say`) or `skills/<name>/SKILL.md` (preferred; same frontmatter: `description`, `argument-hint`, `allowed-tools`, `model`, `disable-model-invocation: true` for user-only commands; `$ARGUMENTS`, `$0`, `$1` substitution). A plugin `settings.json` only applies `agent` and `subagentStatusLine`; every other key is dropped, so the plugin cannot set `statusLine`. `claude plugin validate ./plugin` checks the manifest. Local install for testing: `claude --plugin-dir ./plugins/claude-code`; distribution needs a marketplace entry (`marketplace.json`) or Anthropic's directory.
   - **Update (2026-10-12, https://code.claude.com/docs/en/plugin-marketplaces, https://code.claude.com/docs/en/plugins-reference, `claude plugin --help` 2.1.296):** A marketplace is a directory with `.claude-plugin/marketplace.json` (`name`, `owner`, `plugins[]` with `name` and a `source` relative to the marketplace root, no `..`); one added from a local directory with a relative source reads the plugin files in place, so the launcher `plugins/claude-code/scripts/agentroom.mjs` can resolve `../../../packages/cli/dist/bin.js`. Files in a plugin's top-level `bin/` go on the Bash tool's PATH, so the launcher lives in `scripts/`. `claude plugin install <plugin> --marketplace <path> [--scope user]` adds the marketplace if needed; `claude plugin uninstall <plugin>`; `claude plugin validate <path>`. Plugin skills are invoked as `/plugin-name:skill-name` (https://code.claude.com/docs/en/slash-commands); when no placeholder takes the arguments, Claude Code appends `ARGUMENTS: <input>` to the skill content, so the hook-handled skill bodies never reference `$ARGUMENTS` and `onFailure: "block"` is the primary guard. `claude plugin validate plugins/claude-code` and `claude plugin validate .` (2.1.296) pass. Not verified: the exit code and message of a repeated `claude plugin install` for an already installed plugin; `install claude` treats any non-zero exit as a failure until someone checks it against a real install.
5. **Status line.** Can a plugin set it, or must settings be edited? How to chain with a user's existing status line?
   - **Answer (2026-10-12, https://code.claude.com/docs/en/statusline):** Settings only. `~/.claude/settings.json` (or project settings) gets `"statusLine": {"type": "command", "command": "<path or inline shell>", "padding": 0, "refreshInterval": <seconds, optional>}`. The script receives JSON on stdin (`session_id`, `cwd`, `workspace.current_dir`, `workspace.project_dir`, `model.display_name`, `context_window.used_percentage`, cost fields) and prints the line to stdout; ANSI colors and OSC 8 links are allowed; multi-line output is supported. Updates are event-driven with a 300 ms debounce and go quiet when the session is idle, so set `refreshInterval` (minimum 1) to keep the unread count current. Chaining: `agentroom install claude` saves the user's existing `statusLine.command`, writes `agentroom statusline --chain "<original command>"`, and the script runs the original with the same stdin and appends ` | agentroom ...`; if the original is absent it prints only its own segment. Uninstall restores the saved command.
6. **`UserPromptSubmit` hook.** Can it (a) read the raw prompt, (b) block the prompt from reaching the model, and (c) inject additional context? Exact output format.
   - **Answer (2026-10-12, https://code.claude.com/docs/en/hooks):** (a) Yes: stdin JSON `{"session_id", "transcript_path", "cwd", "permission_mode", "hook_event_name": "UserPromptSubmit", "prompt": "<submitted text>"}` (pasted placeholders arrive expanded). (b) Yes: print `{"decision": "block", "reason": "<shown to the user, not added to context>"}` and exit 0, or exit 2 with the message on stderr. The block message ends with `Original prompt: <text>` unless `hookSpecificOutput.suppressOriginalPrompt: true`; the typed text is still written to the transcript and prompt history, so a hook is not a way to keep text off disk (fine for `/say`, whose text is not secret). (c) Yes: `{"hookSpecificOutput": {"hookEventName": "UserPromptSubmit", "additionalContext": "<string>"}}`, or plain stdout on exit 0, is added alongside the prompt; it cannot replace the prompt. No matcher (fires on every prompt); default timeout 30 s, and a timed-out hook lets the prompt through without context unless `onFailure: "block"`. Declared in settings `hooks.UserPromptSubmit[].hooks[]` or a plugin `hooks/hooks.json` with the same shape.
   - **Update (2026-10-12, https://code.claude.com/docs/en/hooks, https://code.claude.com/docs/en/env-vars):** Hook `additionalContext` and plain stdout are each capped at 10,000 characters (over the cap the text is replaced by a file path and a 2,000-character preview), so `between` delivery stays under 9,000. `UserPromptSubmit` also fires for scheduled tasks, background subagent reports and messages from other sessions. Exec-form hooks take `command` plus `args` with no shell; `onFailure: "block"` (Claude Code 2.1.295 or later) makes a failed or timed-out hook block. Hooks receive `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA` and `CLAUDE_PROJECT_DIR`. `CLAUDECODE` and `CLAUDE_CODE_CHILD_SESSION` are set for Bash tool, hook and status line subprocesses alike; observed in a 2.1.296 Bash tool subprocess, `CLAUDE_PLUGIN_ROOT` is not set, which is what the expansion hook's origin guard relies on. `CLAUDE_CONFIG_DIR` overrides `~/.claude` for settings. The transcript "may lag the in-memory conversation", so the guard does not check it.
7. **Slash commands and hooks.** When the user types a plugin slash command, does the `UserPromptSubmit` hook see the raw text before command expansion? If not, how should `/say` be implemented so the model never sees it?
   - **Answer (2026-10-12, https://code.claude.com/docs/en/hooks, https://code.claude.com/docs/en/slash-commands):** The docs do not state that `UserPromptSubmit` sees raw slash-command text. There is a dedicated **`UserPromptExpansion`** event: it fires "when a user-typed command expands into a prompt, before it reaches Claude" and can block the expansion. Stdin: `{"hook_event_name": "UserPromptExpansion", "expansion_type": "slash_command" | "mcp_prompt", "command_name": "<name>", "command_args": "<args string>", "command_source": "plugin" | ..., "prompt": "/<name> <args>"}`; matcher is on `command_name`; output `{"decision": "block", "reason": "<shown to user>"}` plus optional `hookSpecificOutput.additionalContext`. Decision: `/say`, `/approve` and `/send` are plugin commands (`disable-model-invocation: true`, with a body that only tells the model the hook already handled it, as a fallback) and the plugin's `UserPromptExpansion` hook, matched on those command names, posts the message and blocks the expansion with reason `Sent to <room> as <member> (human)`. A `UserPromptSubmit` hook handles `between` delivery (drains the queue into `additionalContext`) and, defensively, also catches a raw `/say ` prefix if it ever receives one. Commands are now skills; `commands/*.md` still loads.
   - **Update (2026-10-12, https://code.claude.com/docs/en/hooks):** `UserPromptExpansion` stdin also carries `command_source` and the common `transcript_path`; it matches on `command_name`; `decision: "block"` ends the turn and shows `reason` as a warning line; exit 2 also blocks. The docs do not say whether a plugin skill's `command_name` arrives as `say` or `agentroom:say`, nor how `UserPromptExpansion` and `UserPromptSubmit` are ordered. Decision: the matcher is `^(agentroom:)?(say|approve|send|sync-mode)$`; the hook handles `agentroom:<name>`, or a bare name only when the typed prompt starts with `/agentroom:<name>`; `between` delivery skips every prompt that starts with `/`. A real session during the day of use should confirm the `command_name` form.
8. **Channels.** Current status of Claude Code channels (research preview since v2.1.80 per the October 2026 research): capability name, how an MCP server pushes events, launch flag, Team/Enterprise admin requirement.
   - **Answer (2026-10-12, https://code.claude.com/docs/en/channels, https://code.claude.com/docs/en/channels-reference):** Still a research preview. Server declares `capabilities.experimental["claude/channel"] = {}` and pushes `mcp.notification({ method: "notifications/claude/channel", params: { content, meta: { key: value } } })`; the model sees `<channel source="<server>" key="value">content</channel>` (meta keys must be identifiers). Launch: `claude --channels plugin:<name>@<marketplace>` accepts only Anthropic's allowlist (telegram, discord, imessage, fakechat); anything else needs `claude --dangerously-load-development-channels plugin:<name>@<marketplace>|server:<name>`, interactive sessions only (ignored under `-p`). Team/Enterprise need `channelsEnabled: true` in managed settings (Owner); Console API-key users are allowed by default; Pro/Max are allowed. Caveat: on the v2 MCP client runtime Claude Code does not register a channel server that negotiates protocol revision 2026-07-28, and the docs' examples use the v1 `@modelcontextprotocol/sdk` `Server` class. Our server is on SDK v2 (2026-07-28). Decision: M3 ships `between` (hook) and `manual`; `live` via channels is deferred until channels leave preview or accept a 2026-07-28 server. The `send`-side etiquette for a future channel is already in `agentroom-rules`.

   - **Answer (2026-10-12, https://code.claude.com/docs/en/channels "How channels compare"; observed in this build's own harness):** Claude Code offers agent-to-agent and session-to-session messaging within one user's own sessions (local, Remote Control, cloud) plus channels, Slack and cloud sessions. 19. **Desktop notifications.** How should the MCP server raise a notification on macOS and Linux without a dependency that breaks Node 20?
   - **Answer (2026-10-12, `npm view node-notifier`):** `node-notifier` 11.0.0 (published 2026-10-09) declares `engines.node` `^22.22.2 || ^24.15.0 || >=26.0.0`, which excludes Node 20, and ships vendored binaries. 16. **Hosted relay abuse.** Rate limits and size caps are enough for v0? Consider a per-IP room creation cap.
   - **Note for relay-cf (2026-10-12, https://developers.cloudflare.com/durable-objects/best-practices/websockets/, https://developers.cloudflare.com/durable-objects/api/websockets/):** Hibernation API: `this.ctx.acceptWebSocket(server)`; handlers `webSocketMessage(ws, message: ArrayBuffer | string)`, `webSocketClose(ws, code, reason, wasClean)`; `this.ctx.getWebSockets()`; `ws.serializeAttachment(value)` / `ws.deserializeAttachment()` (16 KiB max, survives hibernation while the socket is healthy); in-memory state is reset and the constructor re-runs on wake, so buffer, seq, close key, TTLs and meta go in `ctx.storage`; wrangler binding needs a `durable_objects.bindings` entry plus a migration with `new_sqlite_classes`; the runtime auto-replies to Close frames from compatibility date 2026-04-07. Alarms (https://developers.cloudflare.com/durable-objects/api/alarms/): `ctx.storage.setAlarm(scheduledTimeMs)` (overrides any scheduled alarm), `getAlarm()` returns `number | null`, `deleteAlarm()`, handler `alarm(alarmInfo)` with `alarmInfo.retryCount`; an uncaught exception retries with exponential backoff from 2 s up to 6 times; one `alarm()` runs at a time per object, and the constructor runs before it after inactivity, so the alarm handler must read room state from storage, not memory. `storage.deleteAll()` semantics are on the Storage API page; the relay-cf builder reads it before use. Per-IP creation cap: deferred to the hosted deployment (human step).
   - **Storage `deleteAll` (2026-10-12, https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/):** "For Workers with a compatibility date of `2026-02-24` or later, `deleteAll()` also deletes any active alarm"; earlier dates need `deleteAlarm()`. relay-cf's date is 2026-10-12, and it still calls `deleteAlarm()` after `deleteAll()` before writing the tombstone and its alarm. `setAlarm()` with a past time runs the alarm "in the immediate future"; `deleteAlarm()` does not cancel a running handler.
   - **Local runs (2026-10-12, `npm view`, wrangler 4.149.0 type declarations, and runs on this machine):** `wrangler@4.149.0` declares `engines.node >=22.0.0`; `@cloudflare/workers-types` pinned at `5.20261012.1`. `unstable_startWorker({ config, bindings: { NAME: { type: "plain_text", value } }, dev: { server: { port: 0 }, inspector: false, persist: false, watch: false } })` starts relay-cf on local workerd offline on Node 22+ (checked on 26.5.0); `bindings` override `vars` per run; `worker.url` gives the ephemeral URL and `dispose()` stops it. Worker `console.log` lines come back through wrangler's logger on the test process's `console`, which is how the invariant 1 log check captures them. On Node 20.20.2, `pnpm install --frozen-lockfile` succeeds and the relay-cf test files are skipped (13 + 1 tests), as KTD9 planned. The KTD9 fallback was not needed.
   - **Rate limiting binding (2026-10-17, https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/, wrangler 4.149.0 `config-schema` types, miniflare 5.20261006.1 sources):** No longer `unsafe`: top-level `"ratelimits": [{ "name": "UPGRADE_LIMITER", "namespace_id": "<positive integer as a string>", "simple": { "limit": <n>, "period": 10 | 60 } }]` (wrangler 4.36.0+). Code: `const { success } = await env.UPGRADE_LIMITER.limit({ key })`. "Rate limits that you define and enforce in your Worker are local to the" Cloudflare location where the Worker runs, and the API "is permissive, eventually consistent, and intentionally designed to not be used as an accurate accounting system", so it is a coarse brake, not a hard cap. The docs do not say whether it works inside a Durable Object, so the DO keeps its own in-memory per-address `put` bucket. Local dev: miniflare ships a ratelimit simulator (a Durable Object counting per key per wall-clock window), so `wrangler dev` and `unstable_startWorker` enforce it; tests override the binding by name (`bindings: { UPGRADE_LIMITER: { type: "ratelimit", namespace_id, simple } }`).
   - **Hibernation, tags, auto-response (2026-10-17, https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/, https://developers.cloudflare.com/durable-objects/api/state/, https://developers.cloudflare.com/durable-objects/best-practices/websockets/):** an object with hibernatable WebSockets hibernates "after 10 seconds of inactivity" (so an in-memory token bucket at 2/s with burst 20 has refilled before it is lost). `acceptWebSocket(ws, tags)`: "Each tag is a maximum of 256 characters and there can be at most 10 tags"; `getWebSockets(tag)` filters by tag; disconnected sockets are not returned but closing ones may be. `setWebSocketAutoResponse(new WebSocketRequestResponsePair(req, res))` answers a matching request "without waking WebSockets in hibernation"; each string at most 2,048 characters; `getWebSocketAutoResponseTimestamp(ws)` returns the `Date` of that socket's last auto-response or null. Protocol-level pings: "Incoming ping frames receive automatic pong responses" and do "not interrupt hibernation", so they are invisible to the object; the idle check therefore uses a text `{"t":"ping"}` auto-response.
   - **workers.dev and zone rules (2026-10-17, https://developers.cloudflare.com/waf/rate-limiting-rules/, https://developers.cloudflare.com/workers/configuration/routing/workers-dev/):** WAF rate limiting rules are created "for a zone" (some Enterprise customers can deploy account-level rulesets across Enterprise zones); a `*.workers.dev` hostname is not in a zone the account owns, so no such rule can cover it. Neither page says so directly; that is the inference. To use zone rules, serve the Worker from a custom domain or route and set `"workers_dev": false` (otherwise the next deploy re-enables workers.dev). Free plan: 1 rule, IP counting, 10 s period. The default relay therefore enforces per-address limits in code (`docs/ARCHITECTURE.md`, Abuse limits).
   - **Local server-initiated close (2026-10-17, observed with wrangler 4.149.0 `unstable_startWorker`, Node 26):** when the Durable Object closes a WebSocket on which the client has not yet sent any frame, the `ws` client receives the close frame and replies, but the connection stays CLOSING until the client terminates it; once the client has sent any frame (even an auto-answered ping) the close completes. Not checked on deployed Workers. The hello-timeout conformance test therefore pings before waiting.
   - **Budget alerts (2026-10-17, https://developers.cloudflare.com/billing/manage/budget-alerts/, https://developers.cloudflare.com/billing/understand/usage-based-billing/):** Manage Account > Billing > Billable Usage > Create budget alert (name, USD threshold, email recipients). "Budget alerts are informational only. They do not pause or cap usage." They cover account-wide usage-based spend (not the Workers Paid subscription fee) and reset each billing period; usage is processed once a day, so an alert fires the day after the threshold is crossed. Per-metric "Billable Usage" notifications live under Notifications. The README relay-cf section points operators at both.
